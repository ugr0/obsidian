**CORS（Cross-Origin Resource Sharing）** は、Webブラウザがリソースを異なるドメイン（オリジン）からリクエストすることを制御するためのセキュリティ機構です。これにより、あるウェブページが別のオリジン（ドメイン、プロトコル、ポートの組み合わせ）からリソースを安全にリクエストできるようにします。

### **背景**

通常、Webブラウザは**同一生成元ポリシー（Same-Origin Policy）**を適用します。これにより、あるウェブページ（例えば `https://example.com`）からは、同じオリジンにあるリソース（例えば `https://example.com/api/data`）しかリクエストできません。異なるオリジン（例えば `https://api.example.com`）のリソースには、セキュリティ上の理由からアクセスできません。この制約は、悪意のあるサイトがユーザーの情報を盗んだり、無許可でリクエストを送信したりするのを防ぐためです。

しかし、Webアプリケーションが異なるオリジンからリソースを取得したい場合、**CORS**を使用してこの制限を緩和することができます。

### **CORSの仕組み**

CORSは、サーバーがどのオリジンからのリクエストを受け入れるかを指定するHTTPヘッダーを提供します。サーバーは、リクエスト元のオリジンを確認し、それが許可されていれば、リソースを提供します。

1. **プリフライトリクエスト（Preflight Request）**:
    
    - **GET、POST**などのシンプルなリクエストの場合、CORSはブラウザが自動的にサーバーと通信するのを許可しますが、例えば **PUT** や **DELETE**、またはカスタムヘッダーを含むリクエストを行う場合、ブラウザは**プリフライトリクエスト**を送信します。
    - これは、サーバーに「このリクエストは許可されていますか？」と尋ねるリクエストです。サーバーがそのリクエストに対して許可するレスポンスを返せば、実際のリクエストが行われます。
2. **CORSヘッダー**: サーバーがCORSを有効にするには、特定のヘッダーをレスポンスに追加します。これらのヘッダーは、クライアントにどのオリジンからのリクエストを許可するかを指示します。
    
    例えば：
    
    - **Access-Control-Allow-Origin**: 許可するオリジンを指定します。を指定すると、どのオリジンからのリクエストでも受け入れることになりますが、セキュリティリスクを伴います。
    - **Access-Control-Allow-Methods**: 許可するHTTPメソッド（GET、POST、PUTなど）を指定します。
    - **Access-Control-Allow-Headers**: リクエストに含まれる許可されたカスタムヘッダーを指定します。
    
    サーバーがこれらのヘッダーを設定することで、クライアントが異なるオリジンからリソースを安全にリクエストできるようになります。
    

### **CORSの例**

### サーバー側（レスポンスヘッダー例）：

```
http
コードをコピーする
HTTP/1.1 200 OK
Access-Control-Allow-Origin: <https://example.com>
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: Content-Type, X-Custom-Header

```

このレスポンスでは、`https://example.com` からのリクエストを許可しており、`GET`、`POST`、`PUT` メソッドを使用したリクエストが許可され、`Content-Type` や `X-Custom-Header` ヘッダーも使用可能です。

### クライアント側（JavaScriptの例）：

```jsx
javascript
コードをコピーする
fetch('<https://api.example.com/data>', {
  method: 'GET',
  headers: {
    'Content-Type': 'application/json',
    'X-Custom-Header': 'example'
  }
})
.then(response => response.json())
.then(data => console.log(data))
.catch(error => console.error(error));

```

このクライアント側のリクエストは、`https://api.example.com`からのデータを取得しようとしていますが、サーバーが適切なCORSヘッダーを設定していなければ、ブラウザはリクエストをブロックします。

### **CORSの主なヘッダー**

- **Access-Control-Allow-Origin**: 許可するオリジン（ はすべてのオリジンを許可）
- **Access-Control-Allow-Methods**: 許可するHTTPメソッド（GET、POST、PUTなど）
- **Access-Control-Allow-Headers**: 許可するリクエストヘッダー
- **Access-Control-Allow-Credentials**: 認証情報（クッキーやHTTP認証）を含むリクエストの許可
- **Access-Control-Expose-Headers**: クライアントがアクセス可能なレスポンスヘッダー
- **Access-Control-Max-Age**: プリフライトリクエストの結果をキャッシュする時間（秒単位）

### **CORSのメリット**

1. **セキュリティ**: 同一生成元ポリシーを緩和しつつ、リソースの共有を許可することで、悪意のあるリクエストを防ぐことができます。
2. **柔軟性**: 適切なヘッダーを設定することで、特定のオリジンやメソッドに対してリソースを公開できます。
3. **簡便さ**: Webアプリケーションが複数のサーバーやAPIと連携する場合に、CORSを使用することで安全かつ柔軟にリソースを共有できます。

### **CORSのデメリット**

1. **設定ミスのリスク**: サーバー側でCORSを適切に設定しないと、意図しないオリジンからのアクセスが許可される可能性があります。
2. **複雑性**: 特に複雑なCORS設定が必要な場合、サーバー設定やクライアントの実装が難しくなることがあります。
3. **パフォーマンスの影響**: プリフライトリクエストが必要な場合、リクエストが2回行われることになり、通信コストが増加します。

### **まとめ**

CORSは、異なるオリジン間でリソースを安全に共有できるようにする重要な仕組みです。Webアプリケーションのセキュリティと利便性を両立させるために、適切にCORSヘッダーを設定し、不要なオリジンやリソースへのアクセスを制限することが大切です。
